# 维护模式

维护模式是平台级业务入口门禁，页面为 `/system/maintenance`。API 契约在 `packages/shared/src/ops/contracts/maintenance.ts`，Service 负责生命周期、版本控制和通知。

## 状态与时间

`maintenance_mode` 按唯一业务键 `global` 保存提示草稿与递增版本。`maintenance_logs` 保存维护时段，数据库保证全局最多一个未结束时段；公开状态的 `enabled` 由当前时段是否为 `ongoing` 派生。

| 时段状态 | 页面含义 | 业务门禁 | 可执行动作 |
| --- | --- | --- | --- |
| 无当前时段 | 正常开放 | 不因维护而拒绝 | 保存提示草稿、立即开启、安排计划 |
| `scheduled` | 待开始 | 不因维护而拒绝 | 提前开始、取消计划；重排需取消后新建 |
| `ongoing` | 维护中 | 拒绝无通行能力的普通业务请求 | 更新说明和恢复时间、结束维护 |
| `completed` / `cancelled` | 已结束 / 已取消 | 不作为当前时段生效 | 查询记录与变更详情 |

- 保存提示草稿不会开启维护；开启、更新说明、结束、计划及取消都是显式动作，均填写原因。
- 写入携带读取时的 `version`，事务内共用 PostgreSQL advisory lock；旧版本返回 409，页面保留草稿并要求重载。
- 更新说明或恢复时间保留实际开始时间、开启人和时段 ID；变更过程写入 `changes`。
- `estimatedEndAt` 仅用于预计时间展示；`autoEndAt` 是独立的自动恢复指令，可清空关闭。超过预计时间仍保持维护。
- API 时间使用业务时区 `YYYY-MM-DD HH:mm:ss`，校验日期溢出和时间顺序。

保存配置和执行生命周期动作均递增版本。仅发送提前提醒不改变配置版本。页面收到版本变化后刷新状态和记录，已有草稿继续保留；旧草稿不能覆盖新版本。

## 权限与认证

| 能力 | 权限 |
| --- | --- |
| 查看状态与访问诊断 | `system:maintenance:view` 或 `system:maintenance:manage` |
| 保存、开启、更新、结束及计划 | `system:maintenance:manage` |
| 记录与详情 | `system:maintenance:log` 或 `system:maintenance:manage` |
| 维护期间访问普通业务 | `system:maintenance:bypass`（高风险权限） |

管理能力不授予普通业务通行。维护中具有查看、管理或日志权限的账号可以进入恢复控制台；普通账号显示维护页。通行判定执行完整管理员令牌校验、主体活性及会话撤销检查，并读取当前启用角色和权限。模拟身份不可管理或业务通行。多租户部署仅启用的平台超级管理员可管理全局维护，租户身份即使分配菜单也不可操作。平台超级管理员具有恢复和通行能力，仍受账号状态及会话校验约束。

公开摘要只返回维护文案、时间、版本及生效状态，不返回开启人、通知接收人、操作原因或变更记录。

`GET /access` 返回 `canView`、`canManage`、`canViewLogs`、`canBypass`，页面按服务端返回能力显示操作。
仅有日志权限的账号进入维护记录；仅有业务通行权限不获得维护配置或记录的查看权限。
维护恢复通路只允许维护 API，以及必要的菜单、设置和个人偏好读取；每个 API 仍校验对应操作权限。
HTTP 认证的 Redis 故障策略遵循[安全体系](./security.md#认证令牌)，维护通行不另行提供跳过主体或会话校验的入口。

## API

基址 `/api/maintenance`：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/status` | 公开摘要，`Cache-Control: no-store` |
| GET | `/access` | 当前认证主体的维护能力 |
| GET | `/` | 管理详情、当前时段和版本 |
| PUT | `/` | 完整提交 `version, enabled, message, estimatedEndAt, autoEndAt, reason` |
| GET | `/recipients` | 启用的平台通知接收人 |
| POST | `/plans` | 一次性计划，附加开始时间、自动恢复时间、接收人、提醒分钟数 |
| POST | `/start` | 提前开始，传 `version, reason` |
| POST | `/cancel` | 取消待开始计划，传 `version, reason` |
| POST | `/diagnose` | 当前身份、方法、路径及版本的门禁诊断，与实际请求共用判定 |
| GET | `/logs` | 分页记录，支持状态、关键词及记录创建时间筛选 |
| GET | `/logs/{id}` | 时段详情和变更过程 |

待开始计划通过提前开始或取消处理；重排时取消后新建。诊断只说明维护门禁是否放行，实际业务仍执行路由权限、租户隔离、IP 控制、限流等策略。

### 请求参数

`PUT /api/maintenance` 是完整状态提交，以下字段全部必填：

| 字段 | 规则 |
| --- | --- |
| `version` | 读取时的非负整数版本 |
| `enabled` | 目标状态；`false → false` 保存草稿，`false → true` 开启，`true → true` 更新，`true → false` 结束 |
| `message` | 去首尾空白后 1–512 字符 |
| `estimatedEndAt` | 时间或 `null`；开启或更新进行中维护时必须晚于当前时间 |
| `autoEndAt` | 时间或 `null`；进行中设置时必须晚于当前时间，`null` 关闭自动恢复 |
| `reason` | 去首尾空白后 1–500 字符 |

`POST /plans` 提交 `version`、`message`、`reason`、`estimatedEndAt`、`scheduledStartAt`、`autoEndAt`，以及可选的通知参数：

- `scheduledStartAt` 必须晚于当前时间；非空的预计结束和自动恢复时间必须晚于计划开始时间，两种结束时间互不替代。
- `notifyUserIds` 默认 `[]`，最多提交 100 个正整数用户 ID；服务端去重并加入创建人，目标必须是当前可见且启用的平台账号。
- `remindMinutes` 为 0–1440 的整数，默认 15；0 关闭提前提醒。
- 提交时存在待开始或进行中的时段，返回 409。已过窗口的计划不能提前开始。

`POST /diagnose` 提交 `version`、`method` 和 `path`。方法支持 `GET/POST/PUT/PATCH/DELETE/HEAD/OPTIONS`，路径为 `/api/` 开头、最长 512 字符的路径名，不带查询串。
返回 `allowed`、`reason`、`version`、例外表 `exceptions` 与边界说明 `boundaries`；输入或版本变化后需重新诊断。

`GET /logs` 的 `status` 支持四种时段状态；`keyword` 匹配维护提示、初始原因和开启人，`startTime/endTime` 按记录创建时间筛选。

### 响应语义

| HTTP 状态 | 含义 |
| --- | --- |
| 400 | 参数、日期、时间顺序或通知接收人无效 |
| 401 / 403 | 认证失败，或缺少操作权限 / 平台身份 |
| 404 | 指定维护记录不存在 |
| 409 | 配置版本冲突、已有未结束时段，或当前状态不允许该动作 |
| 503 + `X-Zenith-Error: maintenance` | 业务入口被维护门禁拒绝 |
| 503 + `X-Zenith-Error: maintenance-unavailable` | 维护状态读取失败，不能判断当前业务门禁状态 |

版本冲突时先重载最新状态，再确认和提交修改；不要自动使用新版本重放旧草稿。

## 拦截边界

门禁在认证前 IP 路径限流之后、业务路由之前执行。例外位于 `maintenance-access-policy.ts`，按 HTTP 方法与完整路径模板匹配。健康探测、公开状态、认证必需配置、登录及恢复认证链、经过验签与幂等校验的支付回调继续运行；`/api/auth/*` 和 `/api/ws*` 不是整体豁免范围。

维护拒绝返回 HTTP 503、`X-Zenith-Error: maintenance`、`Retry-After` 和 `Cache-Control: no-store`；响应数据含 `enabled`、`version`、`estimatedEndAt`、`startedAt`。`Retry-After` 是重试建议，不是恢复承诺。
状态读取失败返回 503 与 `maintenance-unavailable`；例外表外的请求不能将未知状态视为正常开放。客户端对此显示服务不可用，不据此进入计划维护提示。状态使用非 SWR 的 5 秒进程缓存，数据库失效总线通知其他节点，监听重建时清空缓存。

控制通道 `GET /api/ws` 保留认证、心跳与维护广播；聊天输入、通话信令等业务帧重新校验通行能力。终端新连接和既有连接输入也受门禁控制。

维护不提供数据库只读保证：已有 HTTP 请求、Worker、Subscriber、关键回调及已开始作业可能继续写入。CMS 非 API 页面、短链和静态资源由部署层控制；全站停写需要配合部署与基础设施措施。

## 计划、通知与恢复

系统调度 `maintenance-lifecycle`（`* * * * *`）由 Worker 每分钟扫描，支持手动执行。提醒、到点开启、显式自动恢复都在全局锁内重读当前时段，不按旧任务载荷操作其他时段。
扫描到开始时间时，若待开始计划的预计或自动结束时间也已到达，直接取消该计划；否则开始维护。
进行中维护只有显式自动恢复时间到达才会自动结束。计划不承诺秒级准点，Worker 不可用或任务停用时不会推进，应检查系统调度配置与执行状态。

立即开启维护时，操作者作为通知接收人；计划维护的创建人和选定平台接收人保存在时段中。安排、开始、更新、结束和取消发送 `ops.maintenance.changed`，提前提醒发送 `ops.maintenance.reminder`；仅保存提示草稿不发送时段通知。
通知与状态同事务落 Outbox，以时段、版本或提醒动作去重。两类事件均为 `important`，默认站内信，可配置邮件；投递遵循渠道策略、个人偏好和免打扰设置，接收人名单不授予维护查看或业务通行权限。投递排查见[通知中心](../notification/index.md)。

后台及其公开分享页按当前身份能力显示维护提示、恢复控制台或业务界面；会员前台和移动审批入口统一显示维护提示。
HTTP 标识或 `maintenance:changed` 控制消息触发公开状态失效，30 秒轮询兜底；恢复后重新校准业务缓存，检查失败保留凭证。
管理员从后台维护提示进入登录和恢复管理，已有账号的通行能力不能沿用到退出后的匿名身份。

浏览器不可用时，在服务器部署目录执行：

```bash
npm run maintenance:recover -- --actor-id <平台管理员ID> --reason "维护完成，恢复服务" --confirm-disable
```

在 monorepo 根目录执行时，加 `-w @zenith/server`；源码开发环境使用 `maintenance:recover:dev`，运行时配置须满足开发环境要求。
命令验证启用的平台账号及当前管理权限，复用版本与事务锁：待开始计划执行取消，进行中维护执行结束，无当前时段时保持正常开放。
恢复原因和操作者写入对应时段；命令不会提供公开 HTTP 绕过入口。数据库不可用时先恢复数据库。部署要求见[部署指南](../guide/deployment.md#维护模式与受控恢复)。

## 记录保留与验收

保留策略按结束时间清理已完成或已取消的时段，默认 365 天；始终保护待开始和维护中的记录，预览与实际删除使用相同筛选条件。
页面支持筛选、时段详情及变更过程，展示动作、操作者、原因、文案、预计结束和自动恢复时间；只读账号没有写入按钮。

验证覆盖：并发开启、旧版本 409、更新不重置开始时间、无效令牌、管理与通行分离、多租户与模拟身份、关键回调、实时业务帧、计划取消/重试/过期窗口、提醒幂等、自动恢复及本地恢复；真实浏览器回归开启、提示、登录恢复、记录详情和窄屏布局。
