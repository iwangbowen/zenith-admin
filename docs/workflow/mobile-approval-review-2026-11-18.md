# 移动审批体验评估与改造方案

> 本文保留首轮浏览器体验记录。代码逐项复核、更正结论及最终实施顺序，以 [移动审批代码复核与最终分阶段方案](./mobile-approval-final-plan-2026-11-18.md) 为准。

评估日期：2026-11-18。入口：http://localhost:5373/approval.html。

## 结论

移动端已有独立入口、待办/已办/我的申请/抄送、发起与草稿、转办、委派、加签、签名、通知及评论等基础能力。简单审批能够完成，但复杂审批的闭环、任务语义和身份缓存尚未与当前 PC 端对齐。建议保留现有入口和后端流程引擎，重整移动端的任务工作台、详情与动作编排；第一阶段先修复账号隔离和阻断问题，再改页面体验。

本轮只进行体验、测试数据准备、源码核对和方案编写，没有修改业务代码，没有提交或部署。无需为历史数据设计兼容分支；以当前 activation / slot / signGroup / task 事实模型统一移动和 PC 行为。

## 实测范围与方式

- 重置库初始只有管理员、CMS 编辑和一条已发布的权限申请流程；权限申请为 custom 表单，移动发起页显示“请到桌面端发起”。
- 新建四名普通测试用户（ID 3–6），并建立专用角色 ID 4，没有给测试用户超级管理员身份。最初使用普通用户角色，以验证真实权限边界；后补充流程处理、代理与打印权限，定位通知问题后再补充消息已读权限。
- 新建表单 ID 6、流程定义 ID 6–10，共 5 条；建立 15 个实例。重复场景用 API 准备，发起、保存、审批等核心体验通过浏览器点击完成；操作后用真实 API 读取持久化结果确认。
- 主体窄屏体验使用 390×844、375×667 CSS 视口。T3 预览后期连续报告浏览器不产生 screenshot frames，切换 ego-browser 补做操作。ego-browser 的视口覆盖会在部分交互后复位，后半段补测不计作全部在手机视口完成。
- 这是桌面浏览器窄屏与部分触控模拟，不代表 iOS Safari、Android WebView、真实软键盘、摄像头和系统分享已验收。

## 已复现问题与优先级

### P0：账号切换缓存隔离

**F01. 换账号后短暂显示上一账号待办。** 通过页面退出王芳，再登录陈晨，auth/me 已是用户 6，pending API 返回 0，界面仍显示王芳的 4 条待办、计数 4。刷新/回源后会恢复，服务端权限没有因此放行。这仍属于不应出现的跨账号数据展示。

根因线索：approval QueryClient 是长生命周期单例；query key 没有账号维度；退出仅清 token，登录没有清理旧查询。见 TaskListPage.tsx:245、LoginPage.tsx:40、lib/queries.ts:24、lib/query-client.ts。

改造：在身份切换边界取消旧请求并清除身份相关缓存，查询按 userId/tenantId/sessionEpoch 隔离；已失效会话的迟到响应不得写入新会话。登录完成前不挂载个人列表和详情。

### P2：现有能力的语义与范围缺口

- **加签与审批组**：移动端固定 position=parallel、signMode=and，缺前/后加签、组级减签、组状态与基础票展示。时间线未传 approvalActivations；PC 已使用冻结轮次/席位/组读模型。canAddSign 仅检查 taskKind=approval，不足以判断原始席位权限，应由能力模型明确是否能创建补充组。后者为源码审查发现，未尝试非法嵌套加签。
- **退回**：移动动作固定 targetNodeKeys=[发起人]，没有合法前序节点选择；PC 已支持目标选择和相应规则。实例 2 时间线任务标签“已驳回”与实例“已退回”并列，需按 decision.action 展示真实动作。
- **委派建议**：已有顶部解释和“待提交建议”，但主按钮/抽屉/Toast 仍为同意、拒绝、已同意，应改为“提交同意建议/提交不同意建议”，回执页显示谁最终确认。
- **草稿**：顶部“草稿 1”点开的是全部我的申请；应路由直达 draft 过滤。新建申请只有手动保存，自动保存仅覆盖已存在草稿；缺离开保护与首次本地草稿。自选人员和抄送设置应纳入草稿模型，不能只保留表单。
- **列表筛选**：流程、优先级、逾期是在已加载数据上过滤，流程下拉也取自已加载数据；并非完整服务端结果。增大 pageSize 的“加载更多”最终超过契约 max=200 会失败。此项由源码/契约确认，未造 200+ 实例压测。
- **协作**：文本评论和抄送阅读已实测；专门的协办发起/回复、减签、撤回已办、动态抄送等入口尚未完整移动化。不要把普通评论当作协办任务。
- **身份入口**：轻页 MFA/强制改密直接要求桌面登录，登录后固定首页；深链登录应恢复原任务，增强认证应在手机完成。这两项是源码确认，未创建 MFA 账号实测。
- **离线承诺**：文案称恢复网络后继续保存，但 online 事件只更新布尔值，没有恢复即补传的明确队列；未保存的新申请也显示同样提示。需补真实断网/重连实验后验收。
- **文档漂移**：mobile-approval.md 仍称无 @/附件/回复、仅同意/驳回/转办；当前代码已有相应部分能力。改造后应同步权威文档，避免重复维护另一套能力说明。

## 建议的信息架构与交互

### 1. 工作台

保留待办、已办、发起、我的申请、抄送五入口。顶部使用当前身份和切换/个人设置入口，通知保留；退出放入个人菜单。按角色提供入口，不让无审批权限的申请人面对错误页。

待办卡片以 taskId 为单位，显示单据标题、当前任务节点、任务类型（正式审批/建议/加签/办理）、发起人、金额等 2–3 项关键摘要、时限和优先级。同实例多任务不去重，但必须一眼可区分。我的申请增加全部/草稿/进行中/已退回/已完成状态筛选，草稿统计直接应用对应条件。列表与筛选、搜索、角标统一服务端口径。

处理后保留原 Tab、搜索、筛选及滚动位置；提供“完成，返回列表”和可设置的“继续下一项”。切到下一项时显示标题和节点，避免无提示自动带入另一张单据。

### 2. 发起与防丢稿

首屏优先业务字段，自动生成标题可展开修改，优先级/抄送收进申请设置。表单底部展示“预计审批路径”，标出自选节点及待满足条件。默认不展开未经过分支和复杂流程图。

首次输入建立本地恢复稿；获得服务端草稿 ID 后自动保存，显示最后保存时间。草稿应保存标题、formData、priority、发起抄送、发起人自选和表单版本引用。中途返回、刷新、重连和提交都采用一致的防丢策略。发布版本变化由服务端进行明确校验和提示，不靠静默套新模板。

### 3. 申请详情

顶部完整标题与状态、业务编号、发起人和当前待办摘要；正文使用“申请内容 / 审批进度 / 沟通”分区或轻 Tab。主操作固定底部“更多 / 拒绝 / 同意”，转办、委派、加签、退回进入统一动作面板。已退回则主按钮变为“修改并重新提交”。

进度先展示正在处理的节点/人和已发生的决策，展开后显示轮次、基础席位计票、前后/并加签组、等待原因和委派建议。流程图作为辅助全屏查看，不作为理解审批状态的必经步骤。并行状态按所有活动节点展示，不能只取 pendingTasks[0]。

### 4. 统一动作面板

动作头显示“对哪张单据、哪个任务做什么”；按当前能力装配意见、附件、签名、选人、加签位置/方式和退回目标。简单动作使用底部 Sheet；包含长表单、签名或多人选择时进入有固定确认条的全屏面板。多人选择展示部门/岗位以区分同名人，采用分页远程搜索，避免每次加载全组织。

确认前明确影响：转办转移任务、委派建议仍需原人确认、加签不会改变基础会签分母、退回会清理/重启哪些轮次。批量仅对符合条件且重新检查状态的任务开放，逐条显示失败与补处理入口。冷却催办显示实际接收人、节点、跳过原因及下次可催办时间。

## 技术改造边界

1. **共用引擎与契约**：不另建移动审批引擎。复用 shared 契约、Server 服务、当前签名/附件体系及幂等能力。PC 与移动共用动作权限与状态投影，只替换表现层。
2. **服务端能力读模型**：由当前用户、实例状态、任务归属、基础席位/建议/加签身份、节点按钮和业务适配器产生 allowedActions。返回动作可用性、禁用原因、意见/附件/签名策略、合法目标与批量资格。客户端不能自行降低服务端授权。
3. **状态模型统一**：详情完整消费 approvalActivations、slots、signGroups、decision、consults、childInstances。避免从任务条数推断会签分母或原始席位身份；任务选择与连续处理均按 taskId。
4. **查询与身份**：个人查询以身份/租户隔离，切换时 cancel+clear；列表采用分页/cursor 的 useInfiniteQuery，服务端完成筛选。失效覆盖列表、计数、详情和消息，不依赖轮询掩盖缺失。
5. **表单呈现**：复用现有字段规则、公式、字段权限；增加移动布局和输入组件映射。日期/枚举/选人用适合触屏的面板，金额数字键盘，明细使用纵向记录卡，复杂输入全屏；不复制业务校验。
6. **业务表单分阶段接入**：designer 首批完成全闭环；custom/external 通过 business adapter 声明移动可发起/查看/动作能力，提供适配页面。暂未适配时在目录明确能力和可用入口，不仅给一个无效灰卡。
7. **不考虑历史兼容**：可直接调整移动 DTO、草稿载荷和前端状态，删除旧分支；当前共享接口发生变化时同步 PC、Mock、OpenAPI 与契约测试。数据库变化使用新迁移，不手改已执行迁移。

## 分阶段实施与验收

### 阶段一：身份与流程闭环

范围：F01–F07、F10，修复退回重提、动作附件、撤回规则、权限错误、消息跳转和快捷审批资格；增加对过期任务/并发处理的状态更新。先不大改视觉。

验收：普通申请人与审批人分别登录均无误导错误；跨账号没有旧身份数据闪现；returned 修改后仍为同实例；必传附件手机可完成；禁止撤回不出现可点按钮；消息已读失败不阻断合法深链；超时/双击/任务已处理不重复推进。

### 阶段二：统一任务语义与复杂操作

范围：能力读模型、轮次/席位/组展示、前后/并加签与减签、合法退回节点、建议回执、协办与撤回已办、F08/F09。

验收：同实例同人多任务可区分且可连续处理；建议回执不算正式票；加签组与基础条件均满足才推进；移动与 PC 对同一实例状态、动作、人员、退回目标和计票完全一致。加入并行、比例会签、顺序会签、子流程和重复轮次回归。

### 阶段三：移动页面体验与可靠保存

范围：工作台/详情/发起信息架构、全屏复杂动作、移动表单控件、人员远程搜索、真正草稿箱、防丢稿、服务端筛选和稳定分页。

验收：375/390/430 宽、横竖屏、长标题、同名人、长表单/明细/附件场景；软键盘不挡确认条；返回保留上下文；断网恢复有真实保存结果；201+ 待办可继续翻页且不误报总数。

### 阶段四：真实设备与业务接入

范围：iOS Safari、Android Chrome/企业 WebView，摄像头/相册、文件预览、系统 PDF 分享、MFA 与登录深链、可移动化的业务表单；生产构建首屏与分包预算。

验收：用真实手机完整重复发起→审批→退回→重提→终审→抄送，覆盖两种身份与中途会话失效。确认手机能力后再扩大业务模块范围。

## 验证方法和本轮边界

实施时稳定业务边界使用 shared/server/查询缓存测试；外观、开合、手势和布局用浏览器及真机验证，遵循项目约束，不用 DOM/CSS 快照固定体验。共享流程变更必须加入独立复杂流程回归，再运行相关领域测试、类型检查、lint 与生产构建预算。

本轮未运行全量自动化测试、构建或性能基准，因为未修改业务实现；未把开发环境模块请求量当生产性能结论。真实断网重连、200+ 待办、实体附件上传/相机、PDF 系统分享、MFA、全部复杂业务表单与真实手机尚未验收。签名成功与后端 evidence 已验证，补测时浏览器最终恢复为桌面尺寸，因此不宣称手写动作完成了真机验收。
