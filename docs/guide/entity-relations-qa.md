## 实际浏览器

在用户打开的 `http://localhost:5373` 上使用真实后端，以管理员身份验证：

1. 支付订单详情关联组可打开，第一屏不查询所有分组。
2. 退款先显示 5 条，继续加载后显示完整 8 条，无重复，分页按钮正确消失。
3. 时间线先显示 20 条，再加载剩余 3 条；包含支付、退款、风控、投诉、通知、任务安全摘要。
4. 复用顶部统一搜索选择测试用户，建立人工关联并即时刷新。
5. 从订单打开目标用户，反向可见同一关联；从用户侧解除后双方刷新。
6. 建立和解除动作可由订单的操作审计分组按结构化主体反查。
7. 顶部搜索结果的“关联信息”按钮正确关闭搜索弹窗并打开关联抽屉。
8. 390 × 844 视口下检查抽屉、长标题、分组、反向关联与解除操作，随后恢复默认视口。
9. 分包优化后重新加载页面，复测首次 Ctrl+K、Esc 与订单详情退款关联列表。

浏览器首次接入曾因 Codex 的 apikey 认证不支持而失败；用户打开浏览器后连接恢复，上述交互验证已实际完成。一次开发热更新期间的时间线请求失败，经界面重试返回 200 并成功验证两页数据。

## 验证中修复的问题

- 关联类型与搜索类型语义分离，数据范围缺失归属列时不再静默放行。
- 改正全量读取后内存分页，锚点租户绑定和微秒级时间游标。
- 取消 Provider 内对所有异常转 404；仅授权后单组查询超时可局部降级。
- 修复分组命名冲突、契约操作 query key 冲突、用户/租户/模拟登录缓存隔离。
- 审计主体写入改为父子事务，签名审计测试替身更新后继续守住图片不入日志的断言。
- 修复两处误用 `List.Item.Meta`，采用 Semi 实际 API；补真组件渲染测试。
- 修复重复 React key、重复空态、搜索结果行内 Portal 冒泡与精确 ID 详情加载。
- 投诉退款的关联与事件进入退款持久化事务，事务失败不会调用支付渠道。
