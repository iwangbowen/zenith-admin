# 性能深度评审与分阶段实施

基线提交：`9e76e184c`。本次针对六类已定位的性能问题实施优化，不增加历史数据、旧接口或旧缓存格式的兼容分支。正确性边界仍包括现有权限、租户隔离、分页、结果预算、流式事件顺序和预览能力。

## 复核结论与方案

| 阶段 | 代码证据与结论 | 实施方案 | 回归重点 |
| --- | --- | --- | --- |
| 1：报表同步计算 | 内存排序在比较器中重复执行带地区配置的 `localeCompare`；超限结果通过二分反复序列化。字段元数据重建还会丢失缓存中的截断标记。 | 复用 `Intl.Collator`，按行累计 JSON 的 UTF-8 字节数，预算触顶即停止；保留结果治理元数据。 | 混合值与空值排序、源数据不变、Unicode/转义/嵌套数据的精确字节数、行数与体积双预算、缓存截断信息。 |
| 2：知识库投影 | 列表、收藏、最近访问以及关闭 snippet 的统一搜索读取正文后丢弃；正文和标题已有 trigram 索引。 | 定义共享轻量列集与对应行类型，按是否需要 snippet 选择搜索投影，详情保留正文。 | SQL 投影不含正文、元数据与关联字段完整、权限条件不变、全文召回及 snippet。 |
| 3：报表计数 | 主库和外部 SQL 驱动均无条件计数，图表和预览不需要完整总数；分页表格需要精确总数。 | 由 `page` / `pageSize` 决定是否计数；非分页 SQL 返回 `total: null`，分页保留精确总数。无需另加运行开关。同步更新预览展示与 Mock。 | 主库及三种外部 SQL 方言的调用次数、分页空页、参数绑定、行权限、缓存与表格。 |
| 4：AI 流式渲染 | 每个 delta 都执行全文修复并更新整页消息状态，侧栏与对话配置的引用不稳定；React 批处理不能跳过事件回调中的计算。 | 合并流式刷新，稳定重型子树的 props 与 memo 边界；在 saved/done/error/停止和断流时保证尾部内容、ID、状态一致。 | 突发事件的刷新次数、reasoning/tool/reference、saved 后消息定位、取消/切换/卸载、侧栏渲染次数。 |
| 5：关联批量解析 | 反向主体按 32 条候选分批读取，但候选逐个查库鉴权；同一事务连接上的 Promise.all 无法消除往返。 | 按对象类型批量解析可见锚点，复用领域权限谓词，消除逐对象 SQL；保留有界扫描和签名游标。 | 批量查询次数、混合类型、跨租户与无权限目标、隐藏批次、分页不重不漏、预算与域失败。 |
| 6：文件预览 | 预览面板已 lazy，但虚拟模块静态注册全部格式，且所有 @file-viewer 模块强制同组，会合并原本可按需加载的依赖。 | 按文件格式加载渲染器并细分构建分组；保留 worker/wasm 资源部署与格式能力。 | 不同格式的加载隔离、重复预览复用、异常重试、主题、三入口生产预算及 Demo 冒烟。 |

## 验证方式

每阶段先执行相关测试与静态检查，再提交独立 commit。最终执行 Shared、Server、Web 回归和 lint，以及生产构建、三入口 bundle 预算、Demo 构建与冒烟。数据库验证使用本地环境与临时事务/测试数据；不得把纯函数微基准推算为端到端 HTTP 吞吐提升。

构建数字取当前生产产物，不能复用 `docs/frontend/perf/current-bundle.json` 的 2026-09-05 快照。执行计划中的耗时、缓冲区与实际请求查询次数作为数据库优化证据；前端使用渲染计数、流式事件回归和构建静态依赖闭包验证。

## 实施记录

各阶段的结果、验证命令和局限随对应提交更新。

### 阶段 1

- 抽出无 I/O 的 `report-result-processing.ts`，供执行引擎复用；无排序时不再复制整个快照。
- 修复元数据装配和二次预算检查丢失截断信息的问题，已有截断在缓存往返后仍保留。
- `npm run test -w @zenith/server -- report-result-processing.test.ts report-dataset.service.test.ts report-materialization.service.test.ts report-security.test.ts report-dashboard-runtime.test.ts`：5 个文件、42 项通过；改动文件 ESLint 通过。
- Node 24.21，5000 行合成数据，直接调用修改后的函数，对照从基线提交提取的原函数；各运行 7 次、去除前 2 次预热。排序中位耗时 826.79 → 21.04 ms；体积截断 74.88 → 2.84 ms；返回行与字节数一致。此处仅度量同步算法，不代表接口端到端提升。

### 阶段 2

- 列表、收藏、最近访问和 `includeSnippet: false` 搜索统一使用无正文的投影；需要 snippet 的搜索仍读取正文，召回和排序条件保持一致。
- 相关 Server 回归 5 个文件、53 项通过；投影调整后复跑文档与片段测试 10 项通过；Server TypeScript 与改动文件 ESLint 通过。
- `NODE_ENV=development LOG_LEVEL=warn node --import tsx scripts/verify-wiki-projection.ts`：在本地 PostgreSQL 事务临时表中验证实际服务列表、正文召回、关闭 snippet 和生成 snippet。20 篇约 200 KiB 正文的文档，全行结果 4,106,323 bytes，元数据投影 9,763 bytes；元数据逐字段一致。临时表自动删除，未写入业务表。
- 浏览器 `localhost:5373/wiki/docs`：正文详情、正文关键词“工牌”搜索及片段、收藏空态与添加/移除、最近访问均通过；收藏恢复原状。

### 阶段 3

- 主库、外部 PostgreSQL / MySQL / SQL Server 的非分页取数不执行 COUNT，返回 `total: null`；分页和空页仍返回精确总数。

- `verify-report-counting.ts` 在真实 PostgreSQL 查询 250000 个生成值，非分页 / 分页分别记录 5 / 6 次执行（均包含相同的 4 条只读护栏）；分页总数为 125000，越界空页总数仍为 125000。一回性角色探测在观测前完成。
- 浏览器：现有 SQL 数据集试跑显示实际“返回 2 行”，计算字段保留；`/report/dashboards/4/view` 的 KPI 和全部 6 行非分页表格正常。外部 MySQL / SQL Server 本轮使用驱动桩验证，未连接实际外部服务。
